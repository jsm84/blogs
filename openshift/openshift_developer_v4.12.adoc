=== Conventions and Requirements [[conventions_requirements]]

This section covers essential commands and workflows that are expected to be utilized for the rest of the guide.

==== Using a Simple Git Workflow [[simple_git_workflow]]

The most basic git workflow will suffice to complete any code changes required in this guide.
Such an example is outlined in this section.

Checkout the application git repo:

  git clone https://git.example.com/example/repo

Change to the repo directory:

  cd repo

Make the desired changes:

  vim README.md

Add the changed files to your commit:

  git add -A

Make the commit:

  git commit -m 'initial commit'

Finally, push the changes to the remote git repo:

  git push

==== Using Source-to-Image (S2I) - Basic Workflow Overview [[using_s2i_overview]]

Source-to-Image is an OpenShift specific development workflow, which uses specialized container images prepared for specific developer frameworks.
An OpenShift developer would typically use an S2I image in conjunction with a source repo developed using a supported language or framework.
The workflow is very similar to multi-stage Containerfile builds (start with a builder image, then copy resulting artifacts into a separate app image), which are pre-dated by S2I.

An S2I build can be triggered from an OpenShift project, which would pull the S2I image, checkout the source and build the code.
The S2I image acts as both the "builder" and the "runtime" base image.

The remainder of this section covers using S2I to build an app, changing the codebase in the git repo, and triggering a rebuild.

Start by running `oc new-app`, which will create a new application in the current project (the `~` is _not_ a typo):

  oc new-app <imagestream>:<tag>~https://github.com/example/repo

The rest is (mostly) a repeat of the <<simple_git_workflow,simple git workflow>> from the previous section.

Clone the remote repo:

  git clone https://github.com/org/codebase
  cd codebase/

Make your code changes:

  vi README.md

Add your files, then commit your changes:

  git add README.md
  git commit -m

Push your changes upstream. Github-based projects should have code-commit webhooks preconfigured in OpenShift to automatically trigger builds on a push to the repo (more on this in <<advanced_build_configuration,Advanced Build Configuration>>).
Regardless, you can trigger a rebuild using `oc`:

  oc start-build bc/<build-config-name>

==== Managing Application Builds [[managing_application_builds]]

To start a fresh application build from scratch in the current project:

  oc new-app --name <name> [ -i <imagestream> | --docker-file <dockerfile> ] [--build-env <var>] <source_url>

Below are a few basic operations that can be performed on buildconfigs.

Start an existing build

  oc start-build bc/<name>

Cancel a build:

  oc cancel-build bc/<name>

Delete a build config:

  oc delete bc/<name>

==== Debugging Commands [[debugging_commands]]

This section lists advanced commands used for debugging and checking application output.
Most of these commands require cluster-admin privileges.

Launch a debug shell on a failing pod:

  oc debug pod/<name>

Launch a specific container image and execute a command (such as `sleep`, to keep a failing container running so you can `oc rsh` in):

  oc run --image <registry.example.com/namespace/image:tag> -- sleep 600

Create a pod used for debugging, and execute an ad-hoc command (to the view output of an app running in another pod in another namespace):

  oc debug [--to-namespace=<name>] -- curl -k https://application.example.com:8000

Execute an ad-hoc command on a certain pod/deployment (to check if an app is running/listening on a certain port):

  oc exec deployment/<name> -- curl https://localhost:8000

Invoke an interactive shell session on a particular pod:

  oc rsh pod/<name>

Invoke an interactive shell session on a particular node:

  oc debug node/<name>

Run commands as a different user:

  oc <command> --as <username>

=== Build and Troubleshoot Applications [[build_troublehoot_apps]]

==== Build and Troubleshoot a Source-to-Image (s2i) Application [[build_troubleshoot_s2i]]

Build a node.js application (hastebin) from source using a git repo, with the following requirements:

* Create a GitHub fork of the following repo: https://github.com/jsm84/hastebin-bf
* Pass the `--name` flag to set the desired app name of `hastebin`
* Use `--build-env` to pass a build variable of `npm_config_registry=<url>`
* Create the application in a new namespace called `makehaste`.

Start by creating a new namespace:

  oc new-project makehaste

Now create the application in the namespace:

  oc new-app --name=hastebin https://github.com/<yourfork>/hastebin-bf --build-env npm_config_registry=https://registry.npmjs.org

NOTE: We used the default NPM registry in our build environment variable, but this variable must be set differently in an _offline environment_.

Watch the log from the build pod (hit CTRL+C to exit) and look for failure info:

  oc logs -f bc/hastebin

Use git to clone the source repo, and a linter (or a proper IDE) to fix any issues with json. Refer to the Simplified Git Workflow to commit and push the code to the remote (which is your cloned) git repo.

To restart the failed `hastebin` build after updating the remote repository:

  oc start-build bc/hastebin

Check the logs again and make sure the build completes successfully. Run `oc get pods` to make sure the application pods come up.

Expose a route to access the application with a web browser:

  oc expose svc/hastebin

Fetch the URL from the route with `oc get route` and then open the URL in a browser to test the application.

==== Troublshoot Resource Exhaustion [[troubleshoot_resource_exhaustion]]

Sometimes a pod might not come up due to resource constraints.
It's necessary to be able to identify when this occurs, and adjust the resource limits so the pod will run.

Take the following example `oc get pods` output:

  NAME                     READY   STATUS      RESTARTS   AGE
  nginx-example-1-z95lt    0/1     Pending     0          1s

Take a closer look with `oc describe pods`:

  Events:
    Type     Reason            Age   From               Message
    ----     ------            ----  ----               -------
    Warning  FailedScheduling  20s   default-scheduler  0/1 nodes are available: 1 Insufficient memory. preemption: 0/1 nodes are available: 1 No preemption victims found for incoming pod..

Take a quick look at the deployment[config]:

----
...
spec:
  template:
    spec:
      containers:
      - name: nginx-example
        ...
        resources:
          requests:
            memory: 20Gi <1>
   ....
----
<1> The memory request is more than the available memory of the available node(s).

To fix this, we must lower the requested memory to be within the limit of the available nodes.
In our case, we have a single node cluster w/12GiB of total memory, so the value must be less than this amount.
Memory availability will of course vary across different OpenShift deployments, so the values shown here will likely differ.

NOTE: It's best to request the minimal amount of memory necessary for the application to run, which for a static web server is typically 1GiB or even less.

==== Troubleshoot Containerfile Builds [[build_troubleshoot_container]]

Modify a Containerfile app (hosted at a remote git repo) so that it runs properly

There are two different git projects comprising this example application:

1. https://github.com/jsm84/gosimplehttpserver
    This is a simple go-based web server chosen to serve the example content.
2. https://github.com/jsm84/gohugo-quickstart
    This is a quickstart website generated with `hugo` which uses the https://github.com/theNewDynamic/gohugo-theme-ananke[Ananke] theme.

The application has the following requirements:

* As before, you'll need to fork the https://github.com/jsm84/gohugo-quickstart repo on GitHub so that you can push changes to the repo.
* All resources must be created in a namespace/project named `hugo`.
* The application name of `quickstart`.
* The application must run and be accessible from outside the cluster (from a web browser or cli web client).

Create a new project named `hugo` to satisfy the project naming requirement:

  oc new-project hugo

Launch a new application build. This should default to the `docker` strategy due to the Containerfile at the repo root:

  oc new-app --name=hugo https://github.com/<example-org>/gohugo-quickstart

Fetch the build pod name again (`oc get pods`), and watch the logs until the build completes:

  oc logs -f bc/quickstart

Check the application pod, and you'll see an error:

  $ oc get pods
  NAME                          READY   STATUS                 RESTARTS   AGE
  quickstart-1-build            0/1     Completed              0          13m
  quickstart-855fb499b6-vhjqc   0/1     CreateContainerError   0          37s

Logs are not directly available from the pod, so use `oc describe` to see what happened:

 $ oc describe pod/quickstart-855fb499b6-vhjqc
  ...
  Warning  Failed  2s  kubelet  Error: container create failed: ... level=error msg="runc create failed: unable to start container process: exec: \"/app/simplehttpserver\":  permission denied"

NOTE: See the next section on Debugging Commands that you can use to troubleshoot.
Also note that newer versions of OpenShift may reveal the cause of the issue (as opposed to the generic `permission denied` error) in the `oc describe pod` output.

HINT: Check the Containerfile for errors. Use the https://github.com/containers/common/blob/main/docs/Containerfile.5.md[Containerfile] man-page spec as a reference.
Despite the misleading error message, the issue _does not_ relate to UIDs, file/directory permissions or Security Context Constraints.

==== Overloading S2I Scripts [[overloading_s2i_scripts]]

The "stock" (unmodified, upstream) S2I builder images can have their scripts overloaded (overridden) by providing your own scripts inside the `s2i/bin` directory within the application source repo.

Two scripts are required for S2I:

* `s2i/bin/assemble` script which builds code and reuses artifacts
* `s2i/bin/run` script which gets set as the entrypoint of the container image

NOTE: You must use the `exec` command when calling the `run` script via wrapper, to ensure that the script still runs as PID 1

Reference the S2I image labels to see where the original scripts are located:

  skopeo inspect <transport>://example.com/remote/repository:tag

Or alternatively:

  podman inspect <container-id>

Create a `save-artifacts` script to enable incremental builds for java or node.js with the following requirements:
* The script must stream artifacts to stdout as a tar file (eg: `tar -cf - .m2` for Maven)
* The script must also redirect all other output to `/dev/null`

To inspect an S2I builder image manually (without access to the source repo):

  podman run --name <name> -it rhscl/httpd-24-rhel7 bash
  cat /usr/libexec/s2i/assemble
  cat /usr/libexec/s2i/run
  cat /usr/libexec/s2i/usage
  exit

=== Creating an S2I Builder Image (Legacy) [[creating_s2i_builder_image]]

NOTE: This section relies on the docker daemon/socket (which `podman` does not expose for security reasons), so it is marked as Legacy.

In this section we'll generate a default s2i builder image using the `s2i` tool, which installs the ruby gem `asdf` that serves the working directory contents over http (port 8080 in this example).
Install the `docker` and `source-to-image` packages in RHEL/Fedora if you wish to follow along.

Generate a new S2I image named `my-s2i-builder` using the syntax `s2i create <image-name> <directory-name>`:

  s2i create my-s2i-builder my-s2i-builder

Switch to the newly created build directory, then edit the Containerfile and the scripts in `s2i/` as desired.
Once you've finished editing the scripts, build the s2i image using podman:

  cd my-s2i-builder
  docker build -t quay.io/example/my-s2i-builder:latest .

Create a simple index file in a new source directory:

  cd ..
  mkdir my-s2i-src/
  echo '<h1>Hello World!!!</h1>' > my-s2i-src/index.html

With the builder image ready, you can create an app image from it using `s2i`:

  s2i build my-s2i-src/ quay.io/example/my-s2i-builder:latest quay.io/example/my-s2i-app:latest

Test the resulting image using podman:

  docker run --name <arbitrary_name> -u 1001 -p 8080:8080 -d s2i-sample-app
  docker ps
  curl http://localhost:8080
  docker stop <name>

If all is well, tag and push the image to the external registry

Create an imagestream in the current project using `oc import-image <name> --from <registry>/<image> --confirm --insecure`

When using `oc new-app`, remember to prefix the git URL using the name of the imagestream created in the previous step

=== Advanced Build Configuration [[advanced_build_configuration]]
This section covers advanced topics dealing with BuildConfig objects in OpenShift.

To change the log level to verbose for a specific build:

  oc set env bc/<name> BUILD_LOGLEVEL="4"

==== Post Commit Hooks [[post_commit_hooks]]

To run a command (such as a python script) as a post-commit hook:

  oc set build-hook bc/<name> --post-commit --command -- exec <command> <arg1> <--option>

To run a shell script as a post-commit hook:

  oc set build-hook bc/<name> --post-commit --script="<script> <arg1>..."

==== Build and Deployment Triggers [[build_deployment_triggers]]

There are a few different build triggers supported in OpenShift:
* Config change trigger - this triggers a build whenever the buildconfig itself is modified
* Webhook trigger - triggers a build when the supported remote code repository (such as GitHub or GitLab) gets updated
* Image change trigger - this causes a build to trigger when a container image changes

To set a config change trigger on a build config:

  oc set triggers bc/<name> --from-config

Set a webhook trigger:

  oc set triggers bc/<name> --from-gitlab

Setting an image change trigger:

  oc set triggers bc/<name> --from-image=<project>/<image>:<tag>

To remove a trigger from a buildconfig:

  oc set triggers bc/<name> --from-<source> --remove

NOTE: `oc new-app` creates both a generic and a git webhook (updating a git webhook means you must reconfigure the git service for the newly created URL)

To test a generic webhook, obtain the webhook URL and run the following curl command:

  oc describe bc/<name>
  curl -X POST -k <webhook_url>

You can test an image change trigger using the following procedure:

  oc new-app --name <name> s2i~registry.example.com:5000/some/image
  oc logs -f bc/<name>
  oc get pods
  oc describe bc/<name> | grep Triggered
  <push a new image>
  oc import-image s2i:latest -n openshift (requires cluster-admin role)

=== Using ConfigMaps [[using_configmaps]]
Configure an application to use a configmap.

Create a configmap:

  oc create cm/<name> --from-literal=<key>=<value>

Set deployment environment variables from a configmap:

  oc set env deployment/<name> --from cm/<name>

To see the vars in a deployment:

  oc set env deployment/<name> --list

Set environment variables in a deploymentconfig:

  oc set env dc/<name> --from cm/<name>

To see env vars in a deploymentconfig:

  oc set env dc/<name> --list

To see active environment vars in a running container:

  oc rsh <podname> env | grep <value>

Export the configmap to a json formatted file:

  oc get cm/<name> -o json > <path/to/output.json>

NOTE: When creating secrets using `oc` or `kubectl`, remember to use the `stringData` attribute to enter secret values without encoding.

=== Using Downward API [[downward_api]]

Kubernetes exposes object metadata field values (such as `metadata.name`) for use within an object definition.
This section describes the typical way to utilize Downward API in an application.

Take, for example, the following pod yaml definition:

----
apiVersion: v1
kind: Pod
metadata:
  name: downward-example
  namespace: downward-test
spec:
  containers:
  - name: ubi-example
    env:
    - name: POD_NAME
      valueFrom:
        fieldRef:
          fieldPath: metadata.name  <1>
    - name: POD_NAMESPACE
      valueFrom:
        fieldRef:
           fieldPath: metadata.namespace  <2>
    image: registry.access.redhat.com/ubi9/ubi-minimal:latest
    command:
    - "sleep"
    - "3600"
----
<1> Reference to pod name
<2> Reference to pod namespace

You can see both the name of the pod, and the namespace that the pod resides in, are both made available as the environment variables `POD_NAME` and `POD_NAMESPACE`, respectively.

=== Health Probes [[health_probes]]

As with OpenShift administration, you'll need to add liveness and readiness probes to an application, which OpenShift will use to to determine an application's health or readiness state (respectively).

HINT: Liveness and readiness probes are commonly defined for pods in the `openshift` namespaces.
You may find it easier to copy/paste from another pod if you're stuck in an offline environment.

The below example uses a generic `tcpSocket` probe for both liveness and readiness:

----
  ...
  spec:
    containers:
    - name: example
      ...
      ports:
      - containerPort: 9090  <1>
        protocol: TCP  <2>
      livenessProbe:
        initialDelaySeconds: 10
        periodSeconds: 30
        tcpSocket:    <3>
          port: 9090  <4>
        timeoutSeconds:
      readinessProbe:
        initialDelaySeconds: <5>
        periodSeconds: 10  <6>
        tcpSocket:
          port: 9090
        timeoutSeconds: 3  <7>
      ....
----
<1> port the container is listening on
<2> protocol the container is using
<3> probe is set to use generic tcp
<4> port that the probe is targeting
<5> how long to wait before the first probe
<6> how often to run the probe (interval)
<7> how long before a timeout occurs


The following example uses an `httpGet` probe for liveness and readiness.
Notice that there are no delays or timeouts specified, causing the default values to take effect:

----
  ...
    spec:
      containers:
      - name: stock
        ...
        ports:
          - containerPort: 8443 <1>
        readinessProbe:
          httpGet:  <2>
            port: 8443  <3>
            path: /readyz  <4>
            scheme: HTTPS  <5>
        livenessProbe:
          httpGet:
            port: 8443
            path: /livez
            scheme: HTTPS
       ....
----
<1> port the container is listening on
<2> probe is set to use http
<3> port that the probe is targeting
<4> path on web server being targeted
<5> set HTTP or HTTPS accordingly

NOTE: You can also copy the readiness/liveness yaml bits from an example template on the system (check `/usr/share/openshift/examples/quickstart-templates`) or refer to the https://docs.openshift.com/container-platform/latest/rest_api/index.html[OpenShift API spec] to view the schema.

=== Application Templates [[application_templates]]

Application Templates (we'll refer to them simply as templates) are essentially a list of all the resources (kube manifests) that make up any given application... the deployments / pods, services, routes, and so on.
Templates have existed on OpenShift since version 3, and though there is some overlap between templates and helm charts, templates are more streamlined and can be represented as a single yaml file.

To deploy an application from a template:

  oc new-app --file <template.json>

Or for templates that have been added to the `openshift` project:

  oc new-app <template-name>

To view the output of a template:

  oc process <template-name>

To process a template from a file:

  oc process -f <template.yaml>

The `oc process` command can be chained to `oc create` using a pipe, which will create all of the template resources on the cluster:

  oc process -f <template.yaml> | oc create -f -

NOTE: Template parameters are passed to `oc new-app` and `oc process` using the `-p key=value` syntax (`-e` is used to set env vars, not template parameters)

You can also export a template from existing resources:

  oc export is,bc,dc,svc,route --as-template=<name> > mytemplate.yml

Then you can deploy the app template into the current project:

  oc create -f mytemplate.yml

Finally, create an application from the template, where `<template-name>` is the original app name prior to export:

  oc new-app <template-name>

You may need to customize a template in certain circumstances.
Parameter placeholders have a similar syntax to shell variables (eg: `${PARAMETER_NAME}`) within a template.

Parameters are actually defined (and can be given default values) at the end of a template:

  parameters:
    - name: SOURCE_REPOSITORY_URL
      displayName: Source Repository URL
      description: The URL of the repository with your application source code
      value: https://github.com/sclorg/cakephp-ex.git
      required: true
    - name: GITHUB_WEBHOOK_SECRET
      description: A secret string used to configure the GitHub webhook
      generate: expression
      from: "[a-zA-Z0-9]{40}"
    - name: REPLICA_COUNT
      description: Number of replicas to run
      value: "2"
      required: true

Note that two of the parameters are `required` and given default values.
Also note that random string generation is possible when given a character class (such as `[a-zA-Z0-9]`) and a length value (such as `{40}`).

=== OpenShift Pipelines [[openshift_pipelines]]

As an OpenShift developer, you'll need to know how to use OpenShift Pipelines, an open source CI/CD offering based on the upstream Tekton project.

OpenShift Pipelines are comprised of these basic building blocks:

* *Tasks* - yaml definitions outlining a set of _steps_ to perform
** *Steps* - the smallest building block of tekton. Steps define the container image and command/script to run, as well as arguments, working directory, etc.
* *Pipeline* - yaml object made up of a set of _tasks_ that are executed in sequence
** *Finally Tasks* - `finally` tasks run at the end of a pipeline and are always executed, regardless if the pipeline failed or succeeded (useful for cleanup tasks).
** *Workspace* - a shared storage volume used by tasks to receive/provide input/output (respectively)
* *PipelineRun* - a pipeline instance bound to a set of workspaces and credentials, which also contains parameters specific to the CI/CD workflow
* *TaskRun* - executes a task on-cluster with specific input, output and runtime parameters. A `PipelineRun` creates a `TaskRun` for each task in a pipeline.
* *Triggers* - used in conjunction with pipelines to capture external events, then mapping info from the event into parameters used for task input.
** *TriggerBinding* - used to extract fields from an event payload, which get stored as parameters
** *TriggerTemplate* - specifies how the parameters from the `TriggerBinding` should be used

==== Example Task [[example_task]]

Lets take a look at the `buildah` task from the https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/ansible/roles/operator-pipeline/templates/openshift/tasks/buildah.yml[operator-pipelines] project:

----
apiVersion: tekton.dev/v1
kind: Task <1>
metadata:
  name: buildah
spec:
  description: |-
    Buildah task builds source into a container image and then pushes
    it to a container registry. Buildah Task builds source into a container
    image using Project Atomic's Buildah build tool.It uses Buildah's support
    for building from Dockerfiles, using its buildah bud command.
    This command executes the directives in the Dockerfile to
    assemble a container image, then pushes that image to a container registry.
  params: <2>
    - description: Reference of the image buildah will produce.
      name: IMAGE
      type: string
    - default: registry.redhat.io/rhel8/buildah@sha256:a1e5cc0fb334e333e5eab69689223e8bd1f0c060810d260603b26cf8c0da2023
      description: The location of the buildah builder image.
      name: BUILDER_IMAGE
      type: string
    - default: vfs
      description: Set buildah storage driver
      name: STORAGE_DRIVER
      type: string
    - default: ./Dockerfile
      description: Path to the Dockerfile to build.
      name: DOCKERFILE
      type: string
    - default: .
      description: Path to the directory to use as context.
      name: CONTEXT
      type: string
    - default: "true"
      description: >-
        Verify the TLS on the registry endpoint (for push/pull to a non-TLS
        registry)
      name: TLSVERIFY
      type: string
    - default: docker
      description: The format of the built container, oci or docker
      name: FORMAT
      type: string
    - default: ""
      description: Extra parameters passed for the build command when building images.
      name: BUILD_EXTRA_ARGS
      type: string
    - default: ""
      description: Extra parameters passed for the push command when pushing images.
      name: PUSH_EXTRA_ARGS
      type: string
  results: <3>
    - description: Digest of the image just built.
      name: IMAGE_DIGEST
  steps: <4>
    - image: $(params.BUILDER_IMAGE)
      name: build
      computeResources: {}
      script: |
        set -xe

        if [ -z "$(params.CONTEXT)" ]; then
          echo "No bundle added or changed"
          exit 0
        fi

        echo "Building $(params.IMAGE)"
        buildah --storage-driver=$(params.STORAGE_DRIVER) bud \
          $(params.BUILD_EXTRA_ARGS) --format=$(params.FORMAT) \
          --tls-verify=$(params.TLSVERIFY) --no-cache \
          -f $(params.DOCKERFILE) -t $(params.IMAGE) $(params.CONTEXT)

        EXTRA_ARGS=""
        if [[ "$(workspaces.credentials.bound)" == "true" ]]; then
          EXTRA_ARGS+=" --authfile $(workspaces.credentials.path)/.dockerconfigjson"
        fi

        if [[ "$(workspaces.cacert.bound)" == "true" ]]; then
          export SSL_CERT_FILE=$(workspaces.cacert.path)/registry-ca.crt
        fi

        echo "Pushing $(params.IMAGE)"
        buildah --storage-driver=$(params.STORAGE_DRIVER) push \
          $(params.PUSH_EXTRA_ARGS) $EXTRA_ARGS --tls-verify=$(params.TLSVERIFY) \
          --digestfile /digest/image-digest $(params.IMAGE) \
          docker://$(params.IMAGE)

        cat /digest/image-digest | tee /tekton/results/IMAGE_DIGEST
      volumeMounts:
        - mountPath: /home/build/.local/share/containers
          name: varlibcontainers
        - mountPath: /digest
          name: digest
      securityContext:
        privileged: true
      workingDir: $(workspaces.source.path)
  volumes: <5>
    - emptyDir: {}
      name: varlibcontainers
    - emptyDir: {}
      name: digest
  workspaces: <6>
    - name: source
    - name: credentials
      optional: true
    - name: cacert
      optional: true
----
<1> Notice the type meta for the object. A `Task` is a kubernetes custom resource type, which is enabled when the OpenShift Pipelines operator gets installed on a cluster.
<2> The list of parameters for this task. The `params` field is a list of keys and values, along with the data type and an optional default value. These are used as input for the steps defined further down.
<3> In the `results` field, the output from `buildah` is captured into a key named `IMAGE_DIGEST`.
<4> Here is where the `steps` are defined. There is only one step defined in this task, named `build`.
<5> `volumes` can also be explicitly defined for a single task
<6> `workspaces` are shared volumes, which can be used as an IPC (inter-process communication) mechanism to join input and output of separate tasks.

    - name: upstream_repo_branch

    - name: podman_image

    - name: registry-cacert

        - name: revision
          value: $(params.git_branch)
        - name: gitInitImage
          value: $(params.gitInitImage)
      workspaces:
        - name: output
          workspace: pipeline

          workspace: ssh-dir
    ...
  finally: <6>
    - name: upload-pipeline-logs
      taskRef:
        name: upload-pipeline-logs
      when:
        - input: $(params.submit)
          operator: in
          values:
            - "true"
      params:
        - name: pipeline_image
          value: "$(params.pipeline_image)"
        - name: md5sum

        - name: cert_project_id

          value: "$(context.pipeline.name)"
        - name: pipelinerun_name
          value: "$(context.pipelineRun.name)"
        - name: pyxis_api_key_secret_name
          value: "$(params.pyxis_api_key_secret_name)"
        - name: pyxis_api_key_secret_key
          value: "$(params.pyxis_api_key_secret_key)"
      workspaces:
        - name: source
          workspace: pipeline

    - name: show-support-link
      taskRef:
        name: show-support-link
      params:
        - name: pipeline_image
          value: "$(params.pipeline_image)"
        - name: env

<1> Noting k8s type meta again, a `Pipeline` is also a custom resource, enabled similarly to tasks when the OpenShift Pipelines operator is installed.
<2> <3> Parameters and workspaces can be defined at the pipeline level, as with tasks.
<4> <5> Here begins the `tasks` list, which references task names (defined elsewhere) via the `taskRef` field

==== Trigger Example [[trigger_example]]

To close out our OpenShift Pipelines overview (and this guide), let's take a look at how triggers can be used to initiate pipelines.
Using the https://github.com/redhat-openshift-ecosystem/operator-pipelines/blob/main/ansible/roles/operator-pipeline/tasks/operator-hosted-pipeline-trigger.yml[hosted-pipeline trigger] as an example:

----
- name: Create trigger enabling running Hosted pipeline via GitHub webhook <1>
  tags:
    - triggers
  block:
    - name: Create Hosted pipeline Trigger Binding
      kubernetes.core.k8s:
        state: present
        namespace: "{{ oc_namespace }}"
        definition:
          # To see the PR webhook payload, set the logLevel to debug in configmap config-logging-triggers
          # Other GitHub PR webhook payload example: https://docs.github.com/en/developers/webhooks-and-events/webhooks/webhook-events-and-payloads#pull_request
          apiVersion: triggers.tekton.dev/v1alpha1
          kind: TriggerBinding <2>
          metadata:
            name: operator-hosted-pipeline-trigger-binding
            labels:
              app: operator-pipeline
              suffix: "{{ suffix }}"
              env: "{{ env }}"
          spec:
            params: <3>
              - name: git_pr_url
                value: $(body.pull_request.html_url)
              - name: git_fork_url
                value: $(body.pull_request.head.repo.clone_url)
              - name: git_repo_url
                value: $(body.pull_request.base.repo.clone_url)
              - name: git_username
                value: $(body.pull_request.user.login)
              - name: git_commit
                value: $(body.pull_request.head.sha)
              - name: git_commit_base
                value: $(body.pull_request.base.sha)
              - name: env
                value: "{{ env }}"
              - name: preflight_trigger_environment
                value: "{{ preflight_trigger_environment }}"
              - name: image_namespace
                value: "{{ operator_pipeline_pending_namespace }}"
              - name: pipeline_image
                value: "{{ operator_pipeline_image_pull_spec }}"
              - name: quay_oauth_secret_name
                value: "quay-oauth-token"
              - name: kerberos_keytab_secret_key
                value: "krb5-isv-pending.keytab"
              - name: hydra_sso_token_url
                value: "{{ operator_pipeline_hydra_sso_token_url }}"
              - name: static_test_suites
                value: operatorcert.static_tests.isv,operatorcert.static_tests.common

    - name: Create Hosted pipeline Trigger Template
      kubernetes.core.k8s:
        state: present
        namespace: "{{ oc_namespace }}"
        definition:
          apiVersion: triggers.tekton.dev/v1alpha1
          kind: TriggerTemplate <4>
          metadata:
            name: operator-hosted-pipeline-trigger-template
            labels:
              app: operator-pipeline
              suffix: "{{ suffix }}"
              env: "{{ env }}"
          spec:
            params:
              - name: git_commit_base
              - name: git_pr_url
              - name: git_fork_url
              - name: git_repo_url
              - name: git_username
              - name: git_commit
              - name: env
              - name: preflight_trigger_environment
              - name: pipeline_image
              - name: image_namespace
              - name: hydra_sso_token_url
              - name: static_test_suites
            resourcetemplates:
              - apiVersion: tekton.dev/v1
                kind: PipelineRun <5>
                metadata:
                  generateName: operator-hosted-pipeline-run
                  labels:
                    app: operator-pipeline
                    suffix: "{{ suffix }}"
                    env: "{{ env }}"
                    git_commit: $(tt.params.git_commit)
                  annotations:
                    git_pull_request_url: $(tt.params.git_pr_url)
                spec:
                  timeouts:
                    pipeline: "2h"
                    tasks: "1h50m"
                  pipelineRef:
                    name: operator-hosted-pipeline <6>
                  params:
                    - name: git_commit_base
                      value: $(tt.params.git_commit_base) <7>
                    - name: git_pr_url
                      value: $(tt.params.git_pr_url)
                    - name: git_fork_url
                      value: $(tt.params.git_fork_url)
                    - name: git_repo_url
                      value: $(tt.params.git_repo_url)
                    - name: git_username
                      value: $(tt.params.git_username)
                    - name: env
                      value: $(tt.params.env)
                    - name: git_commit
                      value: $(tt.params.git_commit)
                    - name: pipeline_image
                      value: $(tt.params.pipeline_image)
                    - name: image_namespace
                      value: $(tt.params.image_namespace)
                    - name: hydra_sso_token_url
                      value: $(tt.params.hydra_sso_token_url)
                    - name: static_test_suites
                      value: $(tt.params.static_test_suites)
                  workspaces:
                    - name: repository
                      volumeClaimTemplate:
                        spec:
                          accessModes:
                            - ReadWriteOnce
                          resources:
                            requests:
                              storage: 5Gi
                    - name: results
                      volumeClaimTemplate:
                        spec:
                          accessModes:
                            - ReadWriteOnce
                          resources:
                            requests:
                              storage: 100Mi
                    - name: registry-credentials-all
                      volumeClaimTemplate:
                        spec:
                          accessModes:
                            - ReadWriteOnce
                          resources:
                            requests:
                              storage: 100Mi
                    - name: registry-credentials
                      secret:
                        secretName: hosted-pipeline-registry-auth-secret
----
<1> No type meta this time. The Operator Certification Pipeline is actually implemented as a set of ansible roles, which in turn create OpenShift Pipelines objects on a cluster.
<2> This is where the `TriggerBinding` gets defined, which will get created on the cluster
<3> The parameter list is the sole function of the `TriggerBinding`. Notice in the list how we're taking json bodies from requests and assigning them to named parameters.
<4> The `TriggerTemplate` definition begins here. Notice how the `params` list aligns perfectly with those from the `TriggerBinding`.
<5> A `PipelineRun` is defined as part of the `TriggerTemplate`.
<6> The `operator-hosted-pipeline` defined by the `pipelineRef` field, will be executed by this `PipelineRun`.
<7> Lastly, notice the Downward API-esque parameter referencing, which brings the parameter values from the `TriggerBinding` all the way down into the `operator-hosted-pipeline`.
